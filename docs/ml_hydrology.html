Machine Learning in Hydrology

Predicting mean streamflow across the CAMELS basins with tidymodels

Author

Nick Penzel

Introduction

This investigation explores predictive modeling in hydrology using the tidymodels framework and the CAMELS (Catchment Attributes and Meteorology for Large-sample Studies) dataset.

tidymodels is an R framework designed for machine learning and statistical modeling. Built on the principles of the tidyverse, it provides a consistent and modular approach to tasks like data preprocessing, model training, evaluation, and validation. By leveraging the strengths of packages such as recipes, parsnip, and yardstick, tidymodels streamlines the modeling workflow, making it easier to experiment with different models while maintaining reproducibility and interpretability.

The CAMELS dataset is a widely used resource in hydrology and environmental science, providing data on over 500 self-draining river basins across the United States. It includes meteorological forcings, streamflow observations, and catchment attributes such as land cover, topography, and soil properties. This dataset is particularly valuable for large-sample hydrology studies, enabling researchers to develop and test models across diverse climatic and physiographic conditions.

The focus here is predicting mean streamflow for these basins using their associated characteristics. CAMELS has been instrumental in calibrating hydrologic models (parameter tuning in models like SAC-SMA, VIC, and HBV), training machine learning models (deep learning such as LSTMs and regression-based streamflow predictions), understanding model behavior (generalization, uncertainty analysis, and the role of catchment attributes), benchmarking and regionalization (large-scale model comparisons and parameter transfer to ungauged basins), and hybrid modeling (enhancing physics-based models with machine learning for bias correction). A notable study by Kratzert et al. (2019) demonstrated that LSTMs can outperform conceptual models in streamflow prediction.

What’s in the data?

Each record in the CAMELS dataset represents a unique river basin, identified by an outlet USGS NWIS gauge_id. The dataset contains a mix of continuous and categorical variables, including meteorological, catchment, and streamflow summaries.

The data used here are the basin-level summaries. For example, for row 1 of the data (Gage: 01013500), all of the attribute values are areal averages over the drainage basin shown below, while the flow metrics are associated with the outlet gage (in red). dataRetrieval::findNLDI() fetches the basin polygon and upstream flowlines.

The libraries below support the full workflow.

The CAMELS dataset is archived on Zenodo. The file listing contains a set of .txt files (climate, geology, soil, topography, vegetation, hydrology summaries per basin), along with a PDF describing every column. Each file has a direct-download link of the form https://zenodo.org/records/15529996/files/<filename>?download=1, so all downloads point at that root.

root <- 'https://zenodo.org/records/15529996/files'

The documentation PDF provides descriptions for the various columns, many of which are not self-explanatory. download.file pulls it into the data/ directory, with mode = "wb" for binary files like PDFs.

download.file('https://zenodo.org/records/15529996/files/camels_attributes_v2.0.pdf?download=1',  destfile = 'data/camels_attributes_v2.0.pdf', mode = 'wb')

Rather than downloading each .txt data file individually, the download is vectorized. First a vector stores the data types and file names to download.

types <- c("clim", "geol", "soil", "topo", "vege", "hydro")

Using glue, the needed URLs and file names are constructed. Zenodo direct-download links end with ?download=1, so that is appended to the remote URL while the local filename is kept clean.

# Where the files live online ...
remote_files  <- glue('{root}/camels_{types}.txt?download=1')
# where we want to download the data ...
local_files   <- glue('data/camels_{types}.txt')

walk2 from the purrr package applies a function to multiple arguments in parallel, much like map2 works over paired lists. Here it passes each paired element of remote_files and local_files to download.file, with quiet = TRUE to suppress output.

walk2(remote_files, local_files, download.file, quiet = TRUE)

Once downloaded, the data is read into R with readr::read_delim(), again using map to apply the function across the local_files list rather than one file at a time.

# Read and merge data
camels <- map(local_files, read_delim, show_col_types = FALSE)

This gives a list of data.frames, one per file, that need to be merged into a single table on the shared gauge_id column. Since there are more than two tables, a more robust tool than the standard *_join functions is needed. The powerjoin package provides a flexible way to join lists of data.frames, supporting inner, left, right, full, semi, anti, and cross joins. Since all data is to be kept, a full join merges every data.frame in the list by gauge_id.

camels <- power_full_join(camels ,by = 'gauge_id')

Model Building

Splitting the Data

First a seed is set for reproducibility, then the q_mean column is transformed to a log scale. Since it is error prone to apply transformations to the outcome variable within a recipe, this is done a priori. The data is then split into training (80%) and testing (20%) sets, with stratification left off in this minimal example. A 10-fold cross validation dataset is also created to help evaluate multi-model setups.

set.seed(123)
# Bad form to perform simple transformations on the outcome variable within a 
# recipe. So, we'll do it here.
camels <- camels |> 
  mutate(logQmean = log(q_mean))

# Generate the split
camels_split <- initial_split(camels, prop = 0.8)
camels_train <- training(camels_split)
camels_test  <- testing(camels_split)

camels_cv <- vfold_cv(camels_train, v = 10)

Preprocessor: recipe

A recipe declares a preprocessing pipeline once, estimates its parameters on the training data, and reuses it everywhere, across folds, the test set, and new predictions. The visual EDA showed that q_mean, aridity, and p_mean are right skewed and helped by log transformations, and that the relationship between aridity and p_mean is non-linear and helped by an interaction term. A small recipe encodes those decisions.

# Create a recipe to preprocess the data
rec <-  recipe(logQmean ~ aridity + p_mean, data = camels_train) %>%
  # Log transform the predictor variables (aridity and p_mean)
  step_log(all_predictors()) %>%
  # Add an interaction term between aridity and p_mean
  step_interact(terms = ~ aridity:p_mean) |> 
  # Drop any rows with missing values in the pred
  step_naomit(all_predictors(), all_outcomes())

Validating on the Test Data

A model’s ability to predict on new data is the most important part of the modeling process; how well it does on data it has already seen matters far less. With the base R approach, this has to be done carefully, and two common mistakes illustrate why.

The first mistake uses broom::augment directly on the test data, which gives incorrect results because the preprocessing steps defined in the recipe have not been applied to the test data.

nrow(camels_test)
[1] 135
nrow(camels_train)

The second mistake uses predict directly on the test data, which fails for the same reason: the recipe’s preprocessing has not been applied, so the scales are way off.

camels_test$p2 = predict(lm_base, newdata = camels_test)

## Scales way off!
ggplot(camels_test, aes(x = p2, y = logQmean)) +
  geom_point() +
  # Linear fit line, no error bands
  geom_smooth(method = "lm", se = FALSE, linewidth = 1) +
  # 1:1 line
  geom_abline(color = "red", linewidth = 1) +

       x = "Predicted Log Mean Flow",
       y = "Observed Log Mean Flow") +

`geom_smooth()` using formula = 'y ~ x'

The correct approach applies the same preprocessing steps to the test data using prep and bake with the recipe, ensuring the test data is transformed the same way as the training data before predictions.

test_data <-  bake(prep(rec), new_data = camels_test)
test_data$lm_pred <- predict(lm_base, newdata = test_data)

Using a workflow instead

tidymodels provides a framework for building and evaluating models using a consistent and modular workflow. The workflows package bundles a preprocessor (recipe or formula) and a model spec into a single object, then fits them together, making it easier to experiment with different models, compare performance, and ensure reproducibility. Here linear_reg() defines a linear regression model with the lm engine in regression mode, the recipe is added to the workflow, the model is fit to the training data, and the coefficients are extracted.

# Define model
lm_model <- linear_reg() %>%
  # define the engine
  set_engine("lm") %>%
  # define the mode
  set_mode("regression")

# Instantiate a workflow ...
lm_wf <- workflow() %>%
  # Add the recipe
  add_recipe(rec) %>%
  # Add the model
  add_model(lm_model) %>%
  # Fit the model to the training data
  fit(data = camels_train) 

# Extract the model coefficients from the workflow

Switching Models

The real power of this approach is that models and recipes can be swapped out easily. Here a random forest model predicts mean streamflow instead, defined with rand_forest, the ranger engine, and regression mode, then added to the recipe, fit, and evaluated.

rf_wf <- workflow() %>%
  # Add the recipe
  add_recipe(rec) %>%
  # Add the model
  add_model(rf_model) %>%
  # Fit the model

A workflowset approach

workflow_set compares multiple models on the same data, defining a set of workflows, fitting them to the same data, and evaluating their performance using a common metric. Here a workflow_set object with the linear regression and random forest models is fit to the training data and compared with autoplot and rank_results.

wf <- workflow_set(list(rec), list(lm_model, rf_model)) %>%
  workflow_map('fit_resamples', resamples = camels_cv) 

autoplot(wf)

Final Model

The workflow-set comparison told us the random forest wins, so it is fit once more on the full training set to give a single model object to interrogate.

final <- workflow() |>

  add_model(rf_model) |>

Evaluation

# Variable importance (Week 5-2 pattern)
final |>

# Predictions on the test set
